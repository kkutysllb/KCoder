## 用户数据空间组织分析

### 三个独立存储区（无统一总目录）

**A. ~/.kcoder/ — 用户主目录（跨版本保留）**
- `qilin-data/system/data/user-data.json` — KCoder 自管 model profiles（活跃，1.4 KB）
- `engine-data/` — QiongQi 时代遗留（governed-engine.sqlite 299KB + threads/users/memory）
- `qiongqi/config.json` — 旧引擎残留
- `argv.json` / `default_workspace/` — 应用级配置

**B. python-runtime/ — sidecar 运行时（开发模式在仓库内）**
- `.qilin/` — QiLin 引擎自身数据
  - `data/qilin.db` — SQLite 主存储（用户表）
  - `users/<uuid>/memory.json` — 记忆 facts（多用户隔离）
  - `users/<uuid>/agents/` — 子代理运行时数据
  - `.retrieval/memory-fts5.sqlite3` — 记忆全文检索索引
- `.langgraph_api/` — LangGraph Platform checkpoint
  - `.langgraph_checkpoint.{1,2,3}.pckl` — 会话历史 pickle
  - `store.pckl` / `store.vectors.pckl` — 向量存储
- `kcoder_local/` — gateway 自管 JSON（plugins/sub_agents/commands/skills_drafts）
  - 当前为空（用户尚未创建任何此类资源）
- `.kcoder_jwt_secret` — JWT 签名密钥（600 权限）
- `extensions_config.json` — MCP 配置（gateway 启动时自动生成）
- `config.yaml` — QiLin AppConfig（injector 改写）

**C. KCoder/ 仓库内（静态资源）**
- `skills/public/` — 59 个内置技能（只读）
- `overlays/worktree-overlay/` — MCP server 源码

### 数据流：模型 profile 注入链
```
用户 Settings 操作 → user-data.json → injector → config.yaml models 段
                                                  ↓
                                       QiLin signature 热重载
```

### 数据流：gateway 路由直接读写
- memory/skills → 直读直写 `.qilin/users/<uuid>/` 或 `.qilin/data/qilin.db`
- plugins/sub_agents/commands → 直读直写 `kcoder_local/*.json`

### 核心问题

**1. 数据空间碎片化**
- 同一份"用户数据"分散在 4 个不同位置
- 没有统一的数据根目录概念
- 用户无法找到自己的数据进行备份/迁移/清理

**2. 存储位置耦合到开发模式**
- `.qilin/` 和 `.langgraph_api/` 当前位于 `python-runtime/`（仓库内）
- 打包分发后路径会变到 app bundle 内部
- 升级/卸载时用户数据可能丢失

**3. 多版本残留**
- `~/.kcoder/engine-data/` + `qiongqi/` 是 QiongQi 时代数据
- 已无用但仍占用空间（~650 KB）
- 新用户安装会混淆

**4. 安全风险**
- `config.yaml` 明文存储 API key（injector 写入）
- `user-data.json` 中 `modelSecrets` 也是明文 API key
- 与 OS keychain 无集成

**5. 多用户隔离设计不彻底**
- model profile 按用户 UUID 分桶（user-data.json 内）
- memory 按用户 UUID 分目录（.qilin/users/）
- 但 JWT secret / extensions_config / config.yaml 是全局共享
- 多用户同时登录会有冲突

### 建议改进方向
1. **统一数据根**：所有用户数据收归到 `~/.kcoder/`，sidecar 用 `--data-dir` 参数指向
2. **OS keychain 集成**：API key 走 `keytar` / Security framework，不入文件
3. **遗留清理脚本**：首次启动检测 `engine-data/` + `qiongqi/`，提示用户迁移或删除
4. **打包路径策略**：明确区分"应用资源"（随 app 走）和"用户数据"（持久化）
5. **schema 版本号**：每个 JSON 文件加 `version` 字段（user-data.json 已有，其他缺失）

### 新设计文档：docs/用户数据空间组织设计.md
参考 KStock 项目（`~/kk_Projects/KStock/docs/用户数据空间组织设计.md`）的同名文档，
为 KCoder 编写了等价的设计蓝本：

**核心方案**：QiLin 运行真源 + KCoder 产品索引层
- 数据根统一：`~/.kcoder/`（macOS/Win/Linux 一致，避开 Application Support 空格坑）
- 6 大子目录：`config/` `runtime/` `product/` `cache/` `logs/` `backups/`
- 引擎数据移出仓库：`runtime/qilin/`（原 `python-runtime/.qilin/`）
- 凭据安全：API key 走 OS keychain，不再明文存 config.yaml
- 产品索引：`product/kcoder.db` 只存会话分组/代码片段/UI 状态
- 迁移策略：v0.1 散落数据 → v0.2 统一根，幂等自动迁移

### 与 KStock 的差异
- `sandbox.allow_host_bash=true`（编码场景必需，KStock 是 false）
- `product/` 索引代码片段而非研究报告
- `cache/` 含 worktree-overlay（git worktree 缓存）
- 会话标签按工作类型（"前端重构"/"bug 修复"）而非行业

### 实施路线（文档第 11 节）
1. KCODER_APP_DATA_DIR 解析层（Electron 主进程）
2. KCoderDataSpace Python 模块（sidecar）
3. SidecarConfig 改造（默认值来自环境变量）
4. qilin.runtime.yaml 启动前生成
5. QiLin CurrentUser 上下文包装
6. sidecar 协议扩展（workspace/thread/run/file/artifact/group/snippet）
7. product/kcoder.db 产品索引
8. OS keychain 集成（keytar）
9. 跨平台测试 + 迁移幂等性
