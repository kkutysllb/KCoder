# dsh-coding-sidebar 1.0.11

> 本版为 dsh 0.1.5 轮尾「交付物卡片」兼容修复：一处让位、一处补门。

## 修复

- **轮尾接管不再吞掉 `present` 交付卡片**：dsh 0.1.5-alpha.2 起 `present` 工具把显式交付写进
  引擎 Turn 的 `deliverables` 记录（新增 `presented` 字段），内置 ui-deliverables 行据此渲染
  交付卡片。轮尾槽 `conversation.chat.turnTail` 是 **CHAIN**——首个返回非 null 的选择器独占整行
  ——而本插件 priority `-1` 的接管只渲染改动 chips，于是「既改文件又 present」的轮次会把交付
  卡片整段吞掉。现在选择器在**本轮声明过交付时直接让位**（`hasDeclaredDeliveries`，新模块
  `src/client/deliveries.ts`，纯函数、零依赖、可单测），改由内置行渲染 chips + 卡片；由于
  下一处修复，内置行上的 chips 与卡片预览点击仍会回到本插件编辑器。

- **补上 0.1.5 真正在用的打开漏斗**：dsh 0.1.5-rc.2 把 chat 侧打开文件从两道旧门整体搬到了
  `ctx.sidebarRight.openResource(address, options?)`——`IWorkspaces` 已无 `openPath`，
  `session/openWorkspacePath` 只剩 `present` 的服务端原生打开在调用（那条必须原样送到宿主 OS）。
  ui-chat 的 `openFile` 现在传的是 `dsh-resource://file/…` **地址**，交由右侧栏的 tab 类型认领。
  此前 1.0.x 的两道包装在 0.1.5 上都是死代码：工具行路径链接、正文行内文件引用、内置改动
  chips、交付卡片预览**全部落进 DSH 内置右侧栏**，`interceptOpenPath` 偏好形同失效。本版新增
  `wrapSidebarRight`（`src/client/openpath-intercept.ts`）接管这道门：地址在本地按上游
  `parseFileAddress` 的语义解码（`session/<id>/<path>` 与 `absolute/<path>`，含盘符 / UNC /
  段级百分号解码 / 查询串忽略），路由进本插件编辑器；文件夹揭示手势（`'.'` 与工作区根地址）
  仍进资源管理器。

## 说明

- 地址里的 `sessionId` **优先于当前会话**：fork 的文件属于 fork，而 `sessions…current` 是用户
  当前看的那个会话。
- 两种情形明确不抢：非 `dsh-resource://file/…` 地址，以及调用方用 `options.kind` 点名了页面
  类型（那是刻意寻址右侧栏，改道会静默忽略其请求）。两种情形都原样穿透到原方法。
- 旧的两道门保留包装、仅在方法存在时装上，老基线照旧接管；0.1.5 上它们是无害 no-op。
- 已知限制：`options.params.line` 的行定位不保留（编辑器 tab 目前没有行种子），与本次迁移前
  的两道门行为一致——那时也没有行参数。
- 交付卡片自身的「用默认应用打开 / 在文件管理器中显示」走宿主 `/api/present.open` 路由，不经过
  本拦截，行为不变。
