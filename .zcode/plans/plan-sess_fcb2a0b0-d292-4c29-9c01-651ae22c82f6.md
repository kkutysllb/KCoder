# 引擎同步 + 集成层完整重写方案

## 决策依据（铁律：产品适配引擎）

经过对 QiongQi v1.1.1 与 KCoder 现有 engine/ 的深度对比，核心结论：

1. **KCoder 现有 `engine/` 是一个分叉**——它在 QiongQi 基础上叠加了大量"让引擎适配产品"的产物：`routes/compat.ts`(5096 行 KWorks 适配层)、`routes/coding-stages.ts`、`routes/turn-execution.ts`、`turn_finished`/`thread_message*`/`context_compacted` 等引擎从未 emit 的事件命名。这些正是违反铁律的历史包袱。
2. **新引擎纯净**：所有 `/api/*`（KWorks）端点删除，回归 `/v1/*` RESTful 一致前缀；HTTP 层只保留引擎核心能力；models CRUD 不再用 HTTP 暴露（底层 `UserDataStore` 程序化能力完整保留）。
3. **你的决定**：除 skills 与前端 UI 外，全部按新引擎重新设计。

## 阶段 1：同步引擎（engine/ 全量重置）

**策略**：整体替换 `engine/` 内容为 QiongQi v1.1.1，只保留两类 KCoder 资产。

### 1.1 备份与保护
- 创建备份分支 `backup/engine-legacy-before-sync`（git stash 现有改动）
- 提取并暂存 KCoder 资产：
  - `engine/skills/`（73 个 skill，含约 19 个 KCoder 特色）
  - `engine/skills-marketplace/index.json`（产品自管用，见阶段 4）
  - 根目录 `pnpm-workspace.yaml` 的 `onlyBuiltDependencies` 段、`package.json` 的 electron-rebuild scripts（这些是 KCoder 根配置，不在 engine/ 内，天然保留）

### 1.2 同步 QiongQi v1.1.1
- 用 QiongQi 仓库内容全量覆盖 `engine/`（rsync，排除 `.git/node_modules/dist/`、`docs/PROGRESS*.md`、`findings.md`/`task_plan.md`/`progress.md` 等非引擎产物）
- 恢复 KCoder skills：把暂存的 73 个 skill 合并回 `engine/skills/`；其中与 QiongQi 新版 11 个核心 skill 同名的（`code-review`/`debugging`/`tdd`/`web`/`goal`/`planning`/`refactoring`/`review`/`security-review`/`todo`/`git-worktrees`）用上游新版覆盖更新，其余 KCoder 特色 skill 原样保留
- 处理 KCoder 特有的容器化文件：`engine/Dockerfile`、`engine/docker-compose.yml` 暂存后恢复（QiongQi 根目录也有同名，以 KCoder 现有为基准）
- **删除** `engine/skills-marketplace/`（产品侧自管，见阶段 4，不再放引擎里）

### 1.3 工作区配置
- `engine/package.json` 用 QiongQi 新版（version 1.1.1，含 postgres verify 脚本）
- 根 `pnpm-workspace.yaml` 保持现有 `app`/`engine`/`engine/packages/*/*` glob + `onlyBuiltDependencies`
- 根 `package.json` 的 `build:engine`/`test:engine`/`rebuild`/`postinstall` scripts 保留（electron-rebuild 是 KCoder 桌面特有）

### 1.4 安装与构建验证
- `pnpm install`（根 + engine）
- `cd engine && pnpm -r run build` 验证引擎编译通过
- `cd engine && pnpm test:fast` 验证引擎测试

## 阶段 2：重写引擎宿主层（main 进程）

**文件**：`app/main/engine-host.ts`（当前 187 行，几乎全重写）

### 2.1 createCodingAgent 调用对齐
新引擎 `createCodingAgent` 顶层 `apiKey/baseUrl/model` 仍必填、仍有效（作为 fallback + thread 默认模型）。但默认工作模式从 `coding`→`office`，coding app 必须显式锁定：

```ts
const capabilities = QiongqiCapabilitiesConfig.parse({
  skills: {
    enabled: true,
    workModes: { defaultModeId: 'coding' }  // ← 关键：锁定 coding 模式
  },
  subagents: { enabled: true }
})
```

### 2.2 删除旧配置清理 hack
- 现有 `engine-host.ts:60-75` 清理 `config.json` serve.model 的 hack 逻辑删除（新引擎模型管理走产品侧 UserDataStore，不再依赖 serve.model 硬编码）

### 2.3 main 进程新增 model 管理能力
- 持有 `FileUserDataStore` 实例（dataDir 下 `system/data/user-data.json`），通过 IPC 暴露给 renderer：
  - `model:list` → `listModelProfiles(userId)`
  - `model:save` → `saveModelProfile(userId, name, profile, {apiKey})`
  - `model:delete` → `deleteModelProfile(userId, name)`
  - `model:activate` → `activateModelProfile(userId, name)`
  - `model:discover` → 自行实现 `{baseUrl}/v1/models` 拉取（参考旧 compat.ts:265-323 逻辑，迁移到 main 进程）
- 单用户场景 `userId` 用固定值 `'insecure-local-user'`（与引擎 insecure 模式一致）
- preload `window.kcoder.models.*` 暴露这些 IPC 方法

### 2.4 健康检查与启动
- `/health` 端点保留，启动逻辑不变

## 阶段 3：重写 renderer 集成层

### 3.1 `app/renderer/src/services/engine-api.ts`（核心重写）

**端点路径对齐**（新引擎全 `/v1/*`，删除所有 `/api/*`）：

| 功能 | 旧路径 | 新路径 | 状态 |
|---|---|---|---|
| auth | `/api/v1/auth/*` | `/v1/auth/*` | 改前缀 |
| thread CRUD/SSE | `/v1/threads*` | `/v1/threads*` | 不变 |
| goal/todos | `/v1/threads/:id/goal\|todos` | 同 | 不变 |
| approval | `/v1/approvals/:id` | 同 | 不变 |
| user-input | `/v1/user-inputs/:id` | `/v1/user-input/:id` 或 `/v1/user-inputs/:id`（新引擎两个都有） | 对齐 |
| workspace status | `/v1/workspace/status?path=` | `/v1/workspace/status`（query 参数化） | 微调 |
| workspace branches/branch | `/v1/workspace/branches\|branch` | **删除** | 移除或迁移到产品侧 |
| models | `/api/models/*` | **删除**（改 IPC） | 阶段 2.3 处理 |
| skills | `/api/skills*` | `/v1/skills*` + drafts 流水线 | 重写 |
| skills-marketplace | `/api/skills-marketplace` | **删除** | 阶段 4 处理 |
| mcp/plugins/subagents/commands/remote | `/api/*` | **删除**（reserved pending backend） | 移除或保留占位 |
| **execution 投影** | `/v1/threads/:id/turns/:turnId/execution` | **删除** | 见 3.2 |

### 3.2 执行进度（ExecutionView）处理
- `/execution` 端点在新引擎不存在，KCoder 每 1.5s 轮询（`useChat.ts:191,288`）会持续 404
- **最小可用方案**：移除 execution 轮询，DAG 执行进度面板暂时显示「不可用」或基于 SSE `pipeline_stage` 事件做简化展示
- **后续深度方案**（按你"完整重写"要求）：接入新引擎 durable stream `/v1/engine/streams/:streamId/subscribe` + `POST .../ack` 模型，需要先调 governed `engine.start()` 拿 streamId（这是 v1.1 governed graph execution 的对外出口）——列为阶段 3 的深度项

### 3.3 SSE 事件 kind 对齐（`engine-api.ts:617-632`）
重写 EventSource 订阅，对齐新引擎 33 种 RuntimeEventKind（`events.ts:11-44`）：

**改名的 kind**（必须改监听名）：
- `turn_finished` → `turn_completed`（**HIGH**：turn 结束信号）
- `thread_message`/`thread_message_delta`/`thread_message_completed` → `item_created`/`item_updated`/`item_completed` + `assistant_text_delta`（**HIGH**：消息渲染管线）
- `context_compacted` → `compaction_started`/`compaction_completed`
- `plan_updated` → `goal_updated`/`goal_cleared`
- `budget_updated` → `usage`

**删除不存在的 kind 监听**（15 种，旧引擎从未 emit）：`model_call_*`、`agent_invoked/finished`、`skill_invoked/finished`、`execution_updated`、`subagent_*`、`session_*`、`stream_completed`、`tool_call_delta`

**新增监听**（新引擎有、KCoder 应接）：`assistant_reasoning_delta`、`approval_resolved`、`user_input_resolved`、`tool_call_ready`、`tool_result_upload_wait`、`tool_storm_suppressed`、`tool_catalog_changed`、`todos_cleared`、`turn_aborted`、`turn_steered`、`pipeline_stage`、`heartbeat`

### 3.4 store / useChat 联动调整
- `app-store.ts`、`useChat.ts` 中事件处理逻辑按新 kind 重写
- `orchestrationPreference`（`'standard'|'team'`）需确认新引擎 `POST /v1/threads/:id/turns` 是否还接受

## 风险与回退

- **回退点**：备份分支 `backup/engine-legacy-before-sync`，任何阶段失败可 `git reset` 回退
- **主要风险**：SSE kind 重写涉及 `useChat.ts` 核心聊天逻辑，需仔细测试流式文本与 turn 结束
- **execution 端点**：深度接入 durable stream 工作量大，阶段 3 先做最小可用（移除轮询 + pipeline_stage 简化展示），durable stream 留作后续增强
- **discover**：从旧 compat.ts 迁移逻辑到 main 进程，需注意 endpointFormat（Anthropic 用 `x-api-key`，OpenAI 兼容用 `Bearer`）

## 工作量评估
- 阶段 1（同步）：中等，主要是 rsync + skills 合并 + 依赖重建
- 阶段 2（engine-host + IPC models）：中等
- 阶段 3（renderer 集成层）：**大**，engine-api.ts 近乎全重写，SSE/useChat 联动是重点
- 阶段 4（自管功能）：小
- 阶段 5（验证）：中等

建议按阶段 1→2→3→4→5 顺序执行，每阶段验证后再进入下一阶段。
