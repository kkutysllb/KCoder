# QiLin 引擎 vendored 升级 v1.0.0 → v2.0.0

## 目标与范围

把 `vendor/qilin` 从 v1.0.0 升级到上游 v2.0.0（多智能体框架核心改造，25 提交 / 327 文件），保持 KCoder 现有功能（含未提交的 5 条增强线 + MCP 能力清单补丁）不回归。

**范围内**：vendor 引擎版本同步、本地补丁在新基线上重应用、requirements.txt 依赖协调、VENDOR_VERSION 更新、验证 sidecar 可启动。

**范围外**（不在本次做）：①迁移到 v2.0.0 自带的 `app/gateway` 服务面（KCoder 继续用自己的 `kcoder_gateway`，上游 gateway 随 vendor 进来但不启用）；②裁剪 v2.0.0 新增的重型集成依赖（kubernetes/e2b/duckdb 等，全部随 `-e ../vendor/qilin` 安装以保持与上游一致）。

## 关键事实（已调查确认）

- 入口点 `qilin.agents.lead_agent.agent:make_lead_agent` 在 v2.0.0 仍存在，`langgraph.json` 无需改。
- v2.0.0 `agent.py` 改动 180 行，`apply_prompt_template` 调用点移到 **837-846 行（bootstrap）** 和 **919-930 行（default）**；`final_tools` 变量名不变。
- `prompt.py` v1→v2 **零改动**；`tool_search.py` 仅 import 改动（文件末尾上下文不变）→ MCP 补丁可干净 apply。
- `frontmatter.py`（KCoder +4 行已提交补丁）上游 v1→v2 **零改动** → subtree 合并无冲突。
- 引擎核心（`qilin/` 包）**不 import bcrypt/passlib**（bcrypt 仅在 `[gateway]` extra）→ KCoder 可继续用 passlib+`bcrypt<4.1`，**前提：绝不装 `qilin[gateway]` extra**。
- requirements.txt 只有 **2 个必须改的 pin**：`httpx>=0.28.0`、`mcp>=1.29.0,<2.0.0`。

## 实施步骤

### 1. 保全当前未提交工作
- `git diff HEAD -- vendor/qilin/ > /tmp/kcoder-mcp-inventory.patch`（保存 MCP 三文件补丁）
- `git checkout -- vendor/qilin/qilin/agents/lead_agent/agent.py vendor/qilin/qilin/agents/lead_agent/prompt.py vendor/qilin/qilin/tools/builtins/tool_search.py`（丢弃未提交的 vendor 改动，已存 patch）
- `git stash push -m "kcoder-wip-subagent-sidebar-title" -- app/ python-runtime/`（暂存 app + gateway 未提交改动）

### 2. subtree pull v2.0.0
- `git subtree pull --prefix=vendor/qilin qilin-upstream v2.0.0 -m "vendor(qilin): bump to v2.0.0 (multi-agent framework)"`
- 预期唯一可能冲突：`vendor/qilin/config.example.yaml`（KCoder 在 8f31c9a 提交过它）。冲突则取 v2.0.0 版本（`git checkout --theirs`，这只是示例文件，KCoder 活跃配置是 `python-runtime/config.yaml`）。
- `frontmatter.py` / `VENDOR_VERSION` 上游无改动，自动保留 KCoder 版本。

> 注：`git subtree pull` 会产生一个合并提交，这是升级操作的固有机制。

### 3. 恢复未提交工作
- `git stash pop`（恢复 app/ + python-runtime/ 的 5 条增强线；它们不触碰 vendor，无冲突）

### 4. 重新应用 MCP 能力清单补丁（3 文件）
- **`prompt.py`**：`git apply /tmp/kcoder-mcp-inventory.patch` 的对应 hunk（文件未变，干净应用）。
- **`tool_search.py`**：同上 apply 末尾新增的 `get_mcp_inventory_prompt_section` 函数 + import 行（末尾上下文未变）。
- **`agent.py`**：手动编辑（v2.0.0 改动大，补丁无法直接 apply）。在两处 `apply_prompt_template(...)` 调用补 `mcp_tools=final_tools,`：
  - 调用点 A（bootstrap，约 845 行 `skill_names=...` 之后）
  - 调用点 B（default，约 929 行 `skill_names=...` 之后）

### 5. 协调 requirements.txt（python-runtime/requirements.txt）
- `httpx>=0.27.0` → `httpx>=0.28.0`
- `mcp>=1.24.0,<2.0.0` → `mcp>=1.29.0,<2.0.0`
- 其余 pin 不变（`langchain-mcp-adapters>=0.3.0` 已覆盖上游 `>=0.2.2`；passlib/bcrypt 保留供 KCoder gateway 自用）。
- 注释更新：说明 v2.0.0 带来的重型集成依赖随 `-e ../vendor/qilin` 自动安装。

### 6. 更新 VENDOR_VERSION
- Tag: `v1.0.0` → `v2.0.0`；Commit 更新为 v2.0.0 的 commit hash。
- 追加 `LOCAL PATCHES` 段落，记录两处本地 fork：
  1. MCP 能力清单 prompt section（`agent.py` / `prompt.py` / `tool_search.py`）—— 待推回上游。
  2. `frontmatter.py` 白名单加 `"package"` 字段 —— 兼容 KSkills 技能包。

### 7. 重装 venv
- 重建虚拟环境以容纳 langchain 0.x→1.x 大版本跳跃与新增依赖：`cd python-runtime && rm -rf .venv && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`（含 `-e ../vendor/qilin`，预计耗时数分钟，体积明显增大）。
- **绝不**执行 `pip install -e ../vendor/qilin[gateway]`（会强制 bcrypt>=5.0，与 KCoder passlib 互斥）。

### 8. 验证
1. **语法/导入**：`.venv/bin/python -m py_compile` 遍历 `python-runtime/kcoder_gateway/**/*.py`。
2. **引擎入口加载**：`.venv/bin/python -c "from qilin.agents.lead_agent.agent import make_lead_agent; print('ok')"`（验证 langchain 1.x + 新 agent.py + MCP 补丁可导入）。
3. **配置兼容**：若启动报缺 `config_version`/`orchestration`，给 `python-runtime/config.yaml` 补最小段（`config_version: 32` 及默认 `orchestration:`），否则不动。
4. **sidecar 冷启动**：手动起 `langgraph dev` + gateway，确认 QiLin service 起来、`make_lead_agent` 注册成功（不要求真实 LLM key，仅验证启动链路）。
5. 前端 `tsc --noEmit` 无需重跑（本次不动 `app/`）。

## 产出与回滚
- 产物：vendor 升到 v2.0.0 + 本地补丁重应用 + 依赖协调 + sidecar 可启动。
- 回滚：`git revert` subtree 合并提交即可回到 v1.0.0（patch 文件在 /tmp，工作改动在 stash/working tree）。

## 风险提示
- v2.0.0 新增大量集成依赖（kubernetes/e2b/duckdb/exa/tavily/firecrawl/markitdown 等），venv 体积与安装时间显著增加——这是"与上游保持一致"的代价，如后续需瘦身可单独评估（不在本次范围）。
- v2.0.0 是多智能体框架大改，runtime 行为可能与 v1.0.0 有差异；本次只验证启动链路，完整 e2e 行为（需 LLM key）不在本次验证范围。
