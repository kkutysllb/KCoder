# Qiongqi Engine v1.1.2

Release date: 2026-07-27

v1.1.2 turns public `parallel`/`join` graphs into production-grade durable execution. Three or more Agent branches may run independently, complete out of order, recover across process or store reconnection, and produce one deterministic non-empty join. Qiongqi remains engine-only and model-neutral.

## User outcomes

- `AgentGraph` and immutable `GraphRevision` now publish `parallel` nodes with stable branch IDs and owning non-empty joins.
- Fan-out prepares all branch AgentRun/KernelRun identities, caller budgets, reservations, and dispatch intents in one governed-root commit.
- Branch completion is correlated by durable execution identity rather than the root cursor. Independent engine instances may complete different branches without losing sibling state.
- `JoinResult.branches` is ordered by branch ID, so completion order, restart timing, and worker placement do not affect output.
- `wait_all` waits for every branch; `fail_fast` atomically aborts open siblings and persists retryable Kernel cancellation work.
- Root cancellation durably records branch/root cancellation in state, work events, and the root stream before external cancellation. A late branch result is audit-only and cannot reopen state or repeat a join.
- Public branch lifecycle events carry `branchId`. Durable stream replay preserves interleaved branch progress, and live `roi.snapshot.byBranch` reconciles branch cost/value with root totals.
- Branch approvals, external tool/wait completion, and recovery preserve sibling cursors and the pinned graph revision.
- Package typecheck resolves workspace dependencies from source, so a clean CI checkout no longer depends on pre-existing `dist` declarations.

Duplicate suppression, structured context compaction, long-task checkpoints, task/Agent memory isolation, cumulative root budgets, and model/tool effect ledgers remain enforced.

## Public API

`DurableEngine` exposes continuation methods for durable workers and reconstructed instances:

- `flushAgentDispatches(limit)` drains currently claimable dispatch/cancellation work.
- `dispatchActiveAgent(input)` prepares a recovered non-parallel Agent dispatch.
- `dispatchParallelAgents(input)` atomically prepares runnable branches.
- `consumeKernelCompletion(input)` consumes a completion using its persisted execution identity.

Parallel callers must explicitly authorize every branch:

```ts
await engine.dispatchParallelAgents({
  multiAgentRunId,
  prompt,
  requestedBudgets: {
    draft: branchBudget,
    research: branchBudget,
    review: branchBudget
  }
})
```

The engine does not split root limits or infer branch budgets.

## Model neutrality

Parallel branches use the same immutable profile registry and revisioned task/node policies as sequential execution. Downstream products may register any provider, authorize multiple profiles, and advance task policy between physical attempts. There is no provider default, fixed model ID, or `deepseek-chat` fallback.

## Upgrade and operations

- Existing sequential v1.1.1 graphs remain valid. Publish a new graph revision before introducing `parallel`.
- Do not allow v1.1.1 workers to claim a v1.1.2 parallel run.
- PostgreSQL is required for multi-instance production and must pass `QIONGQI_TEST_POSTGRES_URL=... pnpm verify:postgres-engine`.
- SQLite supports development, conformance, and single-process reconstruction through independent connections; it is not a distributed production store.
- Cancellation work is at-least-once after claim expiry. Kernel/provider cancellation must be idempotent by execution identity.
- Nested parallel groups remain unsupported in v1.1.2; the graph compiler rejects them.

See [engine-v1.1.md](../migrations/engine-v1.1.md) for the v1.1.1 upgrade path and [deployment.en.md](../deployment.en.md) for release gates.
